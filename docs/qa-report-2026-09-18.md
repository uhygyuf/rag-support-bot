# QA / Release-Readiness Report — RAG Support Bot

**Date:** 2026-09-18 · **Version under test:** the live n8n instance + `workflow/*.json` in this repo
**Method:** risk-based static analysis + live end-to-end execution against the running workflow
**Note:** this follows a public, Google-style engineering *approach* (risk-based scope, layered
automation, security, accessibility, release gates). It is **not** Google's internal process.

---

## A. Executive summary

**Verdict: CONDITIONAL RELEASE.**

The **website channel** (chat widget → RAG answer → deterministic escalation → ticket →
CRM webhook → Telegram alert) is release-ready: all 106 automated checks pass and the critical
journey was verified end-to-end against the live service, including an injection attempt.

The **email channel** is **not** release-ready. Its logic is correct and the mailbox credentials
work, but n8n's IMAP trigger for Gmail fails to activate intermittently (`Connection ended
unexpectedly`) and the workflow is silently deactivated after an n8n restart. Three fixes were
applied during this pass (one of them to a defect introduced by this QA work itself) and re-tested.

## D. Bug list

### B1 — P1 — Code node crashed at runtime (invalid JS) — FIXED, verified
*Repro:* send mail to the support alias → execution ends in error.
*Actual:* `Prep Email Question` → `SyntaxError: Invalid or unexpected token`.
*Expected:* the node normalises the mail body and passes the question on.
*Root cause:* a backslash escape was lost when the node's `jsCode` was generated and JSON-encoded
round-trip; the JS string literal received a raw newline. Static structure checks could not see it.
*Fix:* rewrote the node with explicit escaping; verified with `node --check`; added regression
guard `T23.1` which parses **every** Code node in every shipped workflow.

### B2 — P1 — Ticket stored the bot's reply instead of the customer's question — FIXED, verified live
*Repro:* ask the widget something outside the knowledge base, then read the `tickets` row.
*Actual:* `question` = "I don't have that information - I've passed your question to our team…".
*Expected:* `question` = the customer's own words.
*Root cause:* the prep node fell back to the Agent's output item, which no longer carries `chatInput`.
*Fix:* read the message from the trigger (`$('When chat message received').first().json.chatInput`)
with a guarded fallback; guard `T4.11`. Verified on the live instance: exec 50 stored the exact customer text.

### B3 — P2 — Personal data committed to a public repo — FIXED
*Actual:* workflow exports embedded the owner's name/e-mail in n8n shared-metadata, and the chat id
appeared in notification nodes.
*Fix:* all shipped workflow JSONs scrubbed to placeholders; guard `T20.4`/`T21.4` rejects any
committed `@gmail.com` address or 9–11 digit id.

### B4 — P1 — Email channel: IMAP trigger activation is unreliable on Gmail — OPEN (workaround known)
*Repro:* restart n8n (or re-publish while Gmail is connected) → the workflow ends up deactivated.
*Actual:* `There was a problem activating the workflow: "Connection ended unexpectedly"`; a retry
usually succeeds, and n8n deactivates the workflow after a failed activation.
*Expected:* the trigger activates and keeps a long-lived connection.
*Root cause:* n8n's IMAP trigger / Gmail IDLE behaviour (widely reported upstream); not a
configuration error — the same credentials log in fine from a plain IMAP client.
*Recommended:* for production use the Gmail node via OAuth2 (or a provider with stable IDLE), and
add an error workflow that alerts when a trigger deactivates. Do not promise the email channel to a
client until this is resolved.

### B5 — P2 — Importing a workflow via the n8n CLI deactivates it — MITIGATED
*Actual:* `n8n import:workflow` + `publish:workflow` do not take effect on a running instance; the
workflow must be published from the UI (or n8n restarted) and credentials are dropped from the
imported copy if the export did not carry them.
*Mitigation:* documented runbook; imports now always assert hard preconditions (e.g. the ticket
`tableId` must be a string) before writing.

### B6 — P3 — Shipped template vs live configuration drift — ACCEPTED
The repo ships a placeholder CRM URL while the live instance points at a real webhook endpoint.
That is intended (template vs deployment) but must be spelled out in the client setup guide.

## F. Remaining risks / limitations / next steps

1. **Email channel** — needs a design change before it can be sold (B4).
2. **Telegram channel** — cannot receive messages while n8n is only reachable on `127.0.0.1`;
   requires a public HTTPS endpoint (VPS or tunnel).
3. **No error-alerting workflow** yet; a deactivated trigger is currently silent.
4. **Ticket review UI** — clients read tickets in Supabase directly; no dashboard.
5. **Test depth** — no load/soak test, no dependency CVE scan, no screen-reader pass;
   the a11y results are a baseline (semantics, labels, contrast) only.
6. **LLM non-determinism** — answer wording varies between runs; tests assert contract
   (citation present, handoff sentence present), never exact prose.
